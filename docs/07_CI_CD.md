## 0 단계 - 개념 정리

### 1. 전통적 배포 방식의 한계와 Docker의 해결 방식

- **문제 상황**: 이미 EC2에 Dockerfile 없이 서버를 배포해 정상 동작 중인 상태에서, Docker 도입 필요성이 이해되지 않아 로드맵 진행 전 확인이 필요했음
- **부족한 개념**: git clone(깃 클론) 후 직접 실행하는 방식과 Docker 기반 배포가 실제로 어떤 차이를 만드는지
- **알게 된 사실**: git clone 방식은 소스 코드만 재현하고 OS/라이브러리/의존성 버전까지는 재현하지 않아 환경 비일치(environment inconsistency) 문제가 발생하며, 한 서버에 여러 애플리케이션을 둘 경우 격리 부재로 의존성 충돌이나 자원 경합이 생김. Docker는 이 두 문제를 이미지(코드+의존성+환경 고정)와 컨테이너 격리로 해결한다는 점
- **섹션**: OS

### 2. Dockerfile과 실행 환경 재현의 관계

- **문제 상황**: Dockerfile을 작성하면 빌드(build)+실행(run) 명령만으로 임의의 EC2 인스턴스에서 동일하게 동작시킬 수 있는지 확인이 필요했음
- **추론한 내용**: Dockerfile만 있으면 명령어 한 줄로 어떤 EC2든 자동으로 정상 동작시킬 수 있을 것이라 추론함
- **검증 결과**: 추론이 절반만 맞았음 — 이미지 자체는 실행 환경을 고정해 동일 동작을 보장하지만, 대상 EC2에 Docker Engine(도커 엔진)이 미리 설치되어 있어야 하고 이미지도 그 인스턴스로 전달된 상태여야 한다는 전제 조건이 확인됨
- **결론**: Docker가 없애는 것은 "애플리케이션 실행 환경 설정" 과정이며, "Docker 자체의 설치 과정"까지 없애주는 것은 아니라는 점
- **섹션**: OS

### 3. Docker 표준 워크플로우

- **문제 상황**: Docker 설치 이후 실제로 어떤 절차로 사용하는지 구체적인 흐름이 이해되지 않아 확인이 필요했음
- **부족한 개념**: build, push, pull, run 각 단계가 어느 위치(로컬/레지스트리/서버)에서 일어나는지
- **알게 된 사실**: Dockerfile 작성 → 로컬에서 build로 Docker Image(도커 이미지) 생성 → Docker Registry(도커 레지스트리)에 push → 대상 서버는 Docker Engine만 설치되어 있으면 pull 후 run(또는 compose up)으로 실행하는 흐름이며, "빌드는 한 곳, 실행은 여러 곳"이라는 구조로 대상 서버는 소스 코드나 의존성을 직접 설치할 필요가 없다는 점
- **섹션**: OS

### 4. Docker Registry의 위치와 호스팅 방식

- **문제 상황**: Docker Registry도 결국 하나의 서버일 텐데, 이를 직접 인스턴스를 생성해 구축해야 하는지 확인이 필요했음
- **추론한 내용**: Registry도 서버이므로 별도로 인스턴스를 생성해 직접 구축해야 할 것이라 추론함
- **검증 결과**: 추론이 틀렸음 — Docker Hub, ECR(Elastic Container Registry)과 같은 관리형(managed) Registry 서비스가 이미 존재해 계정만 생성하면 사용 가능하며, 직접 구축은 사내망 격리 등 특수한 경우에만 필요하다는 점이 확인됨
- **결론**: 이미 AWS EC2 환경을 사용 중이므로 IAM/네트워크 통합 이점이 있는 ECR이 자연스러운 선택이라는 점
- **섹션**: Network

### 5. 프로젝트의 Registry 사용 여부 판별법

- **문제 상황**: 특정 프로젝트가 어떤 Docker Registry를 쓰는지 `docker-compose.yml`만 보고 판단할 수 있는지 확인이 필요했음
- **추론한 내용**: `image: alex-rag` 형태의 설정, 그리고 이후 `image: iasandcb/alex-rag:latest` 형태의 설정을 각각 보고 Docker Hub를 사용하는 것이라 추론함
- **검증 결과**: 첫 번째 추론은 틀렸음 — `build: .`와 접두사(prefix) 없는 이름만 있는 경우는 Registry를 전혀 사용하지 않는 로컬 빌드 구성이었음. 두 번째 추론은 맞았음 — `사용자명/이미지명:태그` 형태에서 접두사가 없으면 Docker CLI가 기본값으로 Docker Hub(`docker.io`)를 가리킨다는 점이 확인됨
- **결론**: Registry 사용 여부와 종류는 이미지 참조(image reference) 문자열의 접두사 유무와 형태로 판별하며, `build:` 필드 존재 여부도 로컬 빌드인지 pull 방식인지 구분하는 근거가 된다는 점
- **섹션**: OS

### 6. Registry 미사용과 로컬 빌드 배포의 차이

- **문제 상황**: Registry를 사용하지 않는 구성이 컨테이너를 쓰지 않는 전통적 배포 방식과 실질적으로 같은 것인지 확인이 필요했음
- **추론한 내용**: Registry가 없으면 컨테이너 미사용 방식(전통적 배포)과 동일할 것이라 추론함
- **검증 결과**: 추론이 틀렸음 — Registry 유무와 무관하게 Dockerfile 기반 빌드 자체가 이미 컨테이너화(containerization)이므로 격리(isolation)와 의존성 패키징 효과는 유지됨. 다만 Registry가 없으면 빌드-실행 분리(decoupling)가 불가능해 배포 대상마다 재빌드가 필요하고, 태그(tag) 기반 버전 관리·롤백(rollback)이 불가능하다는 점이 확인됨
- **결론**: Registry는 컨테이너화 자체의 이점(격리, 재현성)과는 별개로 "빌드-실행 분리"와 "버전 관리"라는 추가 이점을 제공한다는 점
- **섹션**: OS

### 7. Docker 내부 동작 원리

- **문제 상황**: Docker가 실제로 어떤 메커니즘으로 격리와 재현성을 구현하는지 근본 원리가 이해되지 않아 확인이 필요했음
- **부족한 개념**: namespace(네임스페이스), cgroups(control groups), union filesystem(유니온 파일시스템)이 각각 무엇을 담당하고 어떻게 결합되는지
- **알게 된 사실**: namespace는 프로세스/네트워크/파일시스템 등 자원의 가시 범위를 컨테이너별로 격리하고, cgroups는 CPU/메모리 등 자원 사용량 상한을 강제하며, union filesystem(대표적으로 OverlayFS)은 이미지를 읽기 전용 계층(layer)으로 쌓고 컨테이너 실행 시 그 위에 쓰기 가능한 얇은 계층을 추가하는 구조라는 점. Docker는 새로운 격리 기술을 만든 것이 아니라 리눅스 커널 기능을 감싼(wrapping) 도구라는 점
- **섹션**: OS
